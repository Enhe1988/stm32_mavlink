## 结论

## 1. 实际发送的是 MAVLink v1

发送端 `c_library_v2-master/mavlink_helpers.h:226`：

```c
bool mavlink1 = 1;
```

因此即便目录名叫 `c_library_v2-master`，`sendOpticalFlowData()` 使用的 finalize 路径仍强制发送 v1。这与实板截图 `magic=254(0xFE)` 完全一致，不是 H743 把 v2 误认成 v1。

H743 parser 本身兼容 v1/v2。两端 `mavlink_msg_optical_flow_rad.h` 和 `mavlink_msg_distance_sensor.h` 的 diff 仅有注释差异，没有字段或打包代码差异。

| 字段 | 消息/载荷偏移 | 发送端赋值 | 接收端处理 |
|------|---------------|------------|------------|
| X 光流 | 106 / 12 | `(float)flowX / 385.0f` | 保存为 `flow_x_rad`，不在解析时过滤 |
| Y 光流 | 106 / 16 | `(float)flowY / 385.0f` | 保存为 `flow_y_rad` |
| 积分时间 | 106 / 8 | 固定 20000us | 除 1e6 得到秒 |
| 距离 | 106 / 36 | 全局 `distance / 1000.0f` | 米，保存为 `ground_distance_m` |
| 质量 | 106 / 43 | `Q` | 保存为 `flow_quality` |
| 测距 | 132 / 8 | `distance / 10` | cm，保存为 `range_cm` |

106 的载荷长度为 44，CRC_EXTRA=138；132 的 v1 基础载荷长度为 14，CRC_EXTRA=85。当前接收库均支持。

`xiaomai_mavlink.c` 中还保留了 MICOLINK 解码函数，但实际主循环调用的是 MAVLink 发送函数，不能据此把 H743 改为 MICOLINK 协议。

## 2. 发送端 SPI 时钟超出 PMW3901 工作规格

不能依据 `at32f421_clock.c` 中的“120MHz”注释计算。实际配置及库实现如下：

- `src/at32f421_clock.c:127`：`CRM_PLL_SOURCE_HICK`、`CRM_PLL_MULT_15`。
- `inc/at32f421_conf.h:51`：`HICK_VALUE=8000000`。
- AT32 库 `libraries/drivers/src/at32f421_crm.c:557`：HICK 作为 PLL 输入时先除以 2。
- `src/at32f421_clock.c:142`：APB2 不分频。
- `src/xiaomai_pmw3901_spi.c:65`：`SPI_MCLK_DIV_8`。

按这份代码推算：

```text
系统时钟 = 8MHz / 2 × 15 = 60MHz
SPI1 时钟 = 60MHz / 8 = 7.5MHz
```

PixArt 数据手册规定 PMW3901MB 串口时钟上限为 2MHz；7.5MHz 超出规格，读 ID、位移和 SQUAL 的结果不能保证可靠。参考 [PixArt PMW3901MB 数据手册，第 3 页](https://wiki.bitcraze.io/_media/projects:crazyflie2:expansionboards:pot0189-pmw3901mb-txqt-ds-r1.40-280119.pdf)。

建议首先在发送端将 SPI 分频改为 `/64` 验证（按当前 60MHz 为 0.9375MHz，即便将来改为 120MHz 也为 1.875MHz），再检查 `chipId=0x49`、`dIpihc=0xB6` 和 SQUAL。这里给出的是修改建议，本次没有修改外部工程。最终应结合板上 `system_core_clock` 和实际 SCLK 测量确认。

## 3. 定时器实际是 25Hz，积分时间仍填 20ms

发送端 `src/main.c:150`：

```c
tmr_base_init(TMR6, 1199, 1999);
```

APB1 不分频、定时器时钟为 60MHz 时：

```text
频率 = 60000000 / ((1199+1) × (1999+1)) = 25Hz
周期 = 40ms
```

但 ISR 每次只给软件时间戳加 20ms，打包时 `integration_time_us` 也固定为 20000。若每次积分实际覆盖约 40ms，H743 按消息声明的 20ms 除算，速度幅值可能约为实际值的两倍；遇到主循环进一步阻塞，误差还会变化。

此外，`src/xiaomai_vl53_iic.c:338` 把测距间隔设为 37ms，`getDistance()` 中调用 `VL53L1_WaitMeasurementDataReady()`。主循环在读取光流之前每轮先调用它，因此光流采集与发送还受到测距阻塞影响。

应在发送端将光流采集与测距等待解耦，按真实积分窗口填写 dt。H743 当前按接收到的 `integration_time_us` 使用，不建议根据接收间隔静默覆盖，因为传输延迟或丢帧并不等于传感器积分时间。

## 4. PMW 初始化和质量逻辑

`src/xiaomai_pmw3901_spi.c:101` 使用：

```c
if (chipId != 0x49 && dIpihc != 0xB6)
    return 0;
```

这只会在两个 ID 都错误时判失败；任一 ID 错误就应失败时，条件应使用 `||`。而 `src/main.c:239` 直接调用 `pmw3901Init()`，没有检查返回值，因此初始化失败也会继续发包。

主循环 `src/main.c:249–260` 的行为：

1. 从 PMW3901 读取 `deltax/deltay`。
2. 任意方向位移超出 ±240 时将 `QUAL` 设为 0；否则读取 SQUAL 寄存器 0x07。
3. 只有 `QUAL>0` 才把位移累加进 `_flow_sum_x/y`。
4. 每次发送后清空累加值。

所以如果 PMW 读数异常、SQUAL 持续为零，发送端自身就会发出 X/Y=0、quality=0，H743 无法从这批数据恢复有效速度。

H743 的速度门限是 quality≥10，比发送端允许累加的 `QUAL>0` 更严格；1–9 的质量值会原样存储但不进入速度解算。这是观测有效性策略差异，不是解码错误。截图 quality=0 同时不满足两端的有效条件，不应通过将门限降为 0 来掩盖。

## 5. 光流帧距离为零与当前发送源码不吻合

当前源码的 106 距离与 132 距离都来自同一个全局 `distance`，前后连续发送。对 777mm 输入，互操作测试还原：

```text
106.distance = 0.777m
132.current_distance = 77cm
```

之前截图中 106 的原始载荷 `payload[36..39]` 全零，而测距帧能给出正常高度。这不能由当前源码的单位换算解释。需确认板上实际烧录程序是否与这份源码相符，并在发送前观察 `distance` 和局部 `opticalFlow.distance`；也可以比对完整的 TX 字节，暂不据此推断 H743 应改变偏移。

## 7. 当时针对旧发送端的检查建议（历史记录）

1. 先读取发送端 `system_core_clock`，核实当前按源码推算的 60MHz；确认正在运行的程序版本。
2. 将 PMW SPI 调整到不超过 2MHz，检查 `pmw3901Init()` 返回值、`chipId`、`dIpihc`。
3. 观察发送端 `deltax`、`deltay`、`QUAL`、`_flow_sum_x`、`_flow_sum_y`，以及打包前 `opticalFlow` 各字段。
4. 与 H743 接收到的原始光流、质量和距离对比同一组测试值，必要时先发固定值消除传感器变化干扰。
5. 等到原始光流和质量正常，再修正真实积分时间、发送周期及速度比例；高度融合问题单独处理。
